# NOSTOS — правила проекта

Мобильная survival-RPG с автобоем. Древняя Греция, маршрут Одиссея.
Дизайн — `GDD.md`. Математика — `BALANCE.md`. Числа — `balance.json`. Задачи — `SPEC.md`.

---

## Стек

TypeScript + HTML5 Canvas + Vite. Тесты — Vitest.

Зависимости: `typescript`, `vite`, `vitest`. **Больше ничего.** Новый пакет — только после явного разрешения, с объяснением, почему без него нельзя.

Рендер Canvas 2D. Без WebGL, без шейдеров, без игровых движков.

---

## Нерушимые правила

**1. Все числа — из `balance.json`.**
Ни одной магической константы в коде. Понадобилось новое число — сначала в конфиг, потом в код. Единственное исключение: чисто технические константы рендера вроде размера буфера.

**2. Детерминизм.**
Весь ГПСЧ идёт через `core/Rng.ts` с явным сидом. `Math.random()` в коде запрещён. Без этого баланс невозможно проверять.

**3. Фиксированный тик.**
Логика считается шагами по 1/60 секунды через накопитель. Никаких вычислений напрямую от `deltaTime` — иначе на слабом телефоне баланс поедет, а на быстром сломается.

**4. Оружие множит стат, не прибавляется к нему.**
```
ATK_type = stat_atk[type] * (rarityMult * (1 + levelStep * (level - 1)))
```
При аддитивной модели уровень оружия перестаёт влиять на урон уже к третьему острову, и система копий обесценивается. Это проверено расчётом. Не менять.

**5. Наследование уровня при повышении редкости включено.**
`balance.weapons.inheritLevelOnRarityUp` — не выключать и не «оптимизировать». Без него лучший дроп в игре делает игрока слабее.

**6. Три иконки над врагом — ядро игры.**
Считаются от фактических статов, без кеша между кадрами, без приближений. Расхождение иконки с реальным уроном ломает единственный механизм принятия решений в игре.

## Стиль кода

- Имена — английские. Комментарии — русские, только там, где неочевидно **почему**, а не **что**.
- Классы вместо ECS. Прототип маленький, ECS тут оверинжиниринг.
- Модуль не длиннее ~200 строк. Длиннее — разбить.
- Никаких `any`. Строгий режим TypeScript включён.
- Логика и рендер разделены. `core/` и `world/` не знают о существовании canvas.

## Процесс

**Сначала план, потом код.** На любой задаче крупнее одного файла — показать план и дождаться ответа.

**Одна задача — один коммит.** Коммит должен оставлять проект в рабочем состоянии.

**Не выходить за объём фазы.** В `SPEC.md` фазы разделены намеренно. Не делать наперёд то, что относится к следующей фазе, даже если кажется, что это на пять минут.

**После любой правки `balance.json` — прогнать `npm run sim`.** Если автопроверки упали, чинить числа, а не проверки.

---

## Тесты

Обязательны для `core/Combat.ts`, `player/Growth.ts`, `player/Weapon.ts`.

Это три модуля, где ошибка не видна глазами при игре, но убивает баланс.

Опорные значения для `Combat.ts` (при `typeExponent = 1.5`):

| атака / защита | множитель |
|---|---|
| 0.5 | ≈ 0.26 |
| 1.0 | 0.50 |
| 2.0 | ≈ 0.74 |
| 3.0 | ≈ 0.84 |

Если тест упал — чинить код, а не тест.

## Дев-панель

`?dev=1` включает панель. Обязательный минимум: ускорение времени 1×/10×/100×, задание любого стата числом, выдача копий, сброс таймеров респауна, телепорт на остров, показ текущего DPS и чистого DPS по цели.

Панель полностью вырезается из продакшн-сборки.

## Чего не делать

- Не добавлять механики, которых нет в `GDD.md`. Есть идея — сначала обсудить.
- Не «улучшать» баланс по своему усмотрению. Числа меняются только через `balance.json` и после прогона симулятора.
- Не добавлять кнопку атаки. Единственный ввод — движение. Это несущая конструкция всей игры.
- Не делать арт до Фазы 4. До неё — прямоугольники.
- Не использовать `localStorage` до Фазы 3, а когда дойдёт — обязательно с версионированием схемы.
